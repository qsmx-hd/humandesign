TECH SPEC · STEP 2

B3 变量计算器
小程序技术方案

在现有人类图小程序内新增「四变量」模块的完整技术设计：计算链路、数据模型、页面结构与开发排期

——把 B2 的单次服务，变成可复用、可传播、可沉淀数据的工具资产。

技术栈：微信小程序 + 云开发
OVERVIEW

它解决什么问题

一句话定位 B3 不是"又一个测试小程序"，而是B2 服务的三个杠杆：
① 获客杠杆——免费算变量 → 付费约解读
② 交付杠杆——会前让客户先自测，会话直接从洞察开始，不用从普及开始
③ 壁垒杠杆——市面上中文的变量计算工具极少，做到位就是差异化

为什么现在做

B2 做到一定量级，客户一定会问「那我团队呢」。这句话就是 B3 的需求信号，也是通往 B 端大单的桥。

为什么不做独立小程序

你已有云开发小程序。加模块，不新建——复用登录、用户池与支付链路，成本最低。

最小可行范围

只做四变量计算 + 详解 + 分享。不做全盘解读、不做合盘、不做流年——那些是已有能力或后续迭代。

一句话价值

让客户在见你之前就先被自己的变量击中一次，会话转化率与满意度都会明显不同。

SECTION 01

计算链路：这是全方案的技术核心

变量的精度要求远高于类型与通道——要算到 Color 与 Tone 层。理解这条链路，才能判断开发难度与风险。

1.1 从黄道到 Tone 的四层细分

层级每份跨度总数说明
闸门 Gate5.625°64360° ÷ 64，对应易经 64 卦
爻 Line0.9375°384每闸门 6 爻，即 384 爻
色调 Color0.15625°2,304每爻 6 分 → 决定六项分类
音调 Tone0.026°13,824每 Color 再 6 分 → 决定箭头方向与细项
精度要求的实际含义 Tone 层跨度仅 0.026°（约 1.6 角分）。这意味着行星位置的计算误差必须远小于此，否则 Tone 会判错。
好消息：现代星历（如 Swiss Ephemeris）的精度在 0.001 角秒量级，比需求高出四个数量级，完全够用。
真正的风险不在算法，而在于：① 用了精度不足的近似公式 ② 时区与夏令时处理错误。

1.2 完整计算步骤

1
出生数据归一化
出生年月日 + 精确到分钟的时间 + 出生地 → 转 UTC 时刻 + 经纬度。时区与历史夏令时是本步最大的坑，必须用可靠的时区数据库。
2
求 Design 时刻
找出太阳黄道位置比出生时刻提前 88° 的那个时刻（约在出生前 88 天）。需迭代求解——太阳移动速度不均匀，不能简单按 88 天推算。
3
计算两组的行星位置
分别计算 Personality 时刻（出生时）与 Design 时刻的太阳与月亮南北交点位置。变量只用到 Sun 与 Node，不涉及其余行星——这是好消息，计算量可控。
4
映射到闸门 / 爻 / Color / Tone
黄道经度 → 闸门序号 → 爻序号 → Color 序号 → Tone 序号。注意人类图的闸门排列不是从 0° 顺时针等分的，需要用官方的曼陀罗映射表，不能自行推算。
5
取出四个变量
按映射关系读出四个变量的值与箭头方向。

1.3 四个变量的取值来源

变量取值来源归属说明
摄食 DeterminationDesign Sun 的 ColorDesign决定六摄食方式
环境 EnvironmentDesign North Node 的 ColorDesign决定六类环境
动机 MotivationPersonality Sun 的 TonePersonality决定六动机
视角 PerspectivePersonality North Node 的 TonePersonality决定六视角
必须正视：映射关系存在实现差异 关于「哪个变量对应哪颗星的哪一属性」，不同资料与不同软件之间存在细微差异（例如有的把动机归于 Sun 的 Color，有的归于 Tone；上下位置的图面布局各家也不一致）。
这不是可以拍脑袋定的事——判错一个，客户当场就能听出来。
对策（必做）：开发阶段用 3–5 个已知变量的真实案例做交叉验证，比对权威软件（如 Jovian Archive 官方工具、或行业主流出图软件）的输出，四项全部对上才算通过。不要相信任何单一来源，包括本方案。

1.4 时间精度的量化说明

客户常问「我的出生时间只记得大概，行不行」。这里给出可量化的回答：

影响对象每天移动改变 Color 需改变 Tone 需
太阳（约 1°/天）1°≈ 3.7 小时≈ 37 分钟
月亮交点（约 0.05°/天逆行）0.05°≈ 3 天≈ 12 小时
实务结论 变量主要由 Sun 与 Node 决定，两者移动都慢，因此变量对时间的敏感度低于通道和闸门——通常要 30 分钟以上的误差才会改变 Tone 层。
但仍然坚持要求精确到分钟：一是行业标准做法，二是留出安全余量，三是避免客户事后质疑。
可以在输入页加一句：「时间越准，结果越准；只记得大概也能算，但环境一项可能有偏差。」——诚实，且降低预期。
SECTION 02

数据模型

在现有云开发数据库中新增 3 个集合，全部挂在 _openid 下，权限设为「仅创建者可读写」。

2.1 var_profiles — 出生档案

{
  _id: "auto",
  _openid: "用户标识",
  name: "姓名/备注",
  birthDate: "1985-04-12",        // 公历
  birthTime: "14:32",              // 24小时制，精确到分
  timeAccuracy: "exact",           // exact | approximate，影响提示话术
  birthPlace: {
    name: "上海市",
    lng: 121.47, lat: 31.23,
    timezone: "Asia/Shanghai"
  },
  createdAt: "ISO日期",
  updatedAt: "ISO日期"
}

2.2 var_results — 计算结果（含缓存）

{
  _id: "auto",
  _openid: "用户标识",
  profileId: "关联 var_profiles._id",
  engineVersion: "v1.0.0",         // 算法版本，便于日后重算
  determination: { arrow:"L", color:1, key:"appetite",      name:"食欲" },
  environment:   { arrow:"R", color:4, key:"mountains",    name:"山脉" },
  motivation:     { arrow:"L", tone:2,  key:"hope",         name:"希望" },
  perspective:    { arrow:"R", tone:4,  key:"wanting",      name:"欲望" },
  raw: {                            // 保留原始中间值，供核查
    designTime: "ISO日期",
    designSunLon: 123.456, designNodeLon: 78.901,
    personSunLon: 22.333,  personNodeLon: 199.888
  },
  createdAt: "ISO日期"
}
为什么必须存 raw 中间值 一旦客户质疑结果，或者日后发现算法有偏差，没有原始数据就无法追溯。存下四个黄道经度，任何时候都能重算与比对。
这是成本极低、价值极高的设计——多存 4 个数字，换来对结果的可审计性。

2.3 var_teams — 团队档案（二期）

{
  _id: "auto",
  _openid: "创建者标识",
  teamName: "高管团队",
  members: [
    { profileId: "...", name: "张三", role: "CEO" },
    { profileId: "...", name: "李四", role: "COO" }
  ],
  createdAt: "ISO日期"
}
团队表是 B 端大单的入口 当一位高管做完 B2 之后问「那我的班子呢」，var_teams 就是承接这个需求的载体。
它能直接产出团队配置视图：谁需要安静空间、谁需要流动、谁被什么驱动——这些是 HR 与 OD 能直接用的东西，也是从 ¥4,800 单次服务跃升到 ¥25,000 工作坊的桥。
一期先把表结构留出来，二期再开发功能。
SECTION 03

云函数设计

云函数职责优先级
varCalc核心。接收出生数据 → 返回四个变量。纯计算，不写库，便于单独测试P0
varSave调用 varCalc 并写入 var_results，带缓存（同参数直接返回历史结果）P0
varContent按 key 返回对应变量的详解文案（从数据库读，便于运营修改）P1
varShare生成分享卡片（小程序码 + 变量摘要图）P1
varTeam团队聚合分析，输出配置建议（二期）P2

3.1 依赖选型

需求推荐说明
星历计算Swiss Ephemeris 的 JS 移植，或 astronomy-engine精度需达 0.001° 以内。不要用简化的太阳位置近似公式
时区处理带历史时区与夏令时的库（如 Luxon + 完整 tzdata）中国 1986–1991 年实行过夏令时，处理错误会整体偏差一小时
地理编码复用现有小程序的城市库，或接地图服务只需经纬度，不需要逆地理
两个最容易出错的坑 ① 中国夏令时（1986–1991）：这几年出生的人，如果不做夏令时校正，结果会整体偏差约一小时，足以改变 Tone。必须用带历史规则的时间库，不能用固定 UTC+8。
② 云函数体积限制：完整星历表数据较大，可能超出单个云函数的部署限制。对策是只引入太阳与月亮交点的计算模块（变量只用到这两者），或把星历数据放在云存储按需加载。
建议在正式开发前，先做一个「只算太阳位置」的技术验证（spike），确认精度与体积都过关再全面开发。

3.2 计算函数伪代码

// varCalc 主流程
function calcVariables(birthUTC, lng, lat) {

  // 1. 求 Design 时刻：太阳比出生时提前 88°
  const sunBirth = sunLongitude(birthUTC);
  const target   = normalize(sunBirth - 88);
  const designUTC = solveByIteration(
     t => sunLongitude(t) === target,
     birthUTC - 95days, birthUTC - 80days
  );

  // 2. 四个关键黄道经度
  const designSun  = sunLongitude(designUTC);
  const designNode = northNodeLongitude(designUTC);
  const personSun  = sunLongitude(birthUTC);
  const personNode = northNodeLongitude(birthUTC);

  // 3. 映射到 Color / Tone
  return {
    determination: decode(designSun,  'color'),   // → 六摄食
    environment:   decode(designNode, 'color'),   // → 六环境
    motivation:    decode(personSun,  'tone'),    // → 六动机
    perspective:   decode(personNode, 'tone'),    // → 六视角
    raw: { designUTC, designSun, designNode, personSun, personNode }
  };
}

// decode: 黄道经度 → 闸门/爻/Color/Tone 四级
// 必须使用官方曼陀罗映射表，不可自行等分推算
SECTION 04

页面结构与流程

1
入口页
在现有小程序首页加一个「四变量 · 决策环境」入口。文案：「你最清明的状态，藏在四个变量里」。
2
输入页
姓名 + 出生日期 + 时间（精确到分，带"记不清"选项） + 出生地。时间字段要有明确提示，说明精度影响。
3
计算页
加载态展示行星定位动画（约 1–2 秒）。这段时间不要留白，展示"正在定位您的行星坐标"等文案，制造专业感。
4
结果总览页 核心页
四张卡片，每张显示：变量名称 + 你的类型 + 一句话核心。一句话必须击中，这是决定用户会不会继续看的关键。
5
单项详解页
点击卡片进入：核心定义 + 工作场景 + 常见误判 + 本周可做的一个动作。只给一条动作，不要列十条。
6
分享页
生成含四变量摘要的分享卡片 + 小程序码。分享是获客主力，必须做。
结果页的设计要害：一句话核心 用户扫一眼结果页的时间只有几秒。一句话核心决定他会不会往下点。
反例（不要这样）：「您的环境是山脉，代表您适合高处和视野开阔的地方。」——平淡，像说明书。
正例（要这样）：「您需要距离——离得远一点，才看得清。」——有钩子，用户会想知道为什么。
24 项的一句话核心，是文案投入产出比最高的地方，值得单独打磨。

与 B2 服务的联动设计

环节设计
会前发送带参数的链接或小程序码，客户自测后数据自动归档到你的查看端，你提前看到结果，会话直接从洞察开始
会中直接用小程序上的结果页讲解，客户看得见自己的数据，说服力高于纯口述
会后报告里附上小程序码，客户可随时回看自己的四项
转化详解页底部设「约一场 90 分钟深度解读」入口，免费工具 → 付费服务的漏斗
SECTION 05

内容层设计

内容与代码分离 24 项的详解文案全部存数据库，不写在代码里。
理由：文案会反复修改（尤其一句话核心），存库可以随时调整、不用重新发版；也方便日后做多版本（C 端灵性版 / B 端组织版两套话术）。

内容字段设计

{
  key: "environment.mountains",
  kicker: "高度 · 距离 · 视野",
  name: "山脉",
  oneline: "您的身体需要高度和距离——离得远一点，才看得清。",
  scene: "工作场景表现...",
  misread: "常见误判...",
  action: "本周可做的一个动作...",
  variants: {
    b2b: { scene: "...", action: "..." },   // 组织语言版
    b2c: { scene: "...", action: "..." }    // 灵性语言版
  }
}
两套话术的必要性 你同时在做 C 端学员与 B 端客户，同一套内容对两类人的表达必须分开。
B 端客户（尤其企业采购方）看到「觉醒」「无我」「能量场」这类词会本能警惕；C 端学员则觉得组织语言太干。
字段里预留 variants，一期可以只填 B 端版，二期再补 C 端版。

SECTION 07

风险与对策

风险等级对策
计算映射判错高 用 3–5 个已知案例交叉验证权威软件，四项全对才算通过。不相信任何单一来源，包括本方案给出的映射表
时区与夏令时错误高 使用带历史时区规则的库；专门测试 1986–1991 年中国夏令时出生案例
星历库体积超限中 只引入太阳与月亮交点模块；或把数据放云存储按需加载。Sprint 0 必须验证
内容合规中 文案禁用「诊断 / 治疗 / 预测 / 注定」；摄食项只谈工作节奏，绝不出现饮食建议
命名两套混用中 视角项选定一套命名（六视角 或 六感），全站一致，并在页面标注采用来源
免费工具冲击付费中 工具只给「是什么」，不给「对你意味着什么」。详解页要给场景，但落地动作留到付费会话
数据归属与隐私中 出生数据属敏感个人信息。需明示收集目的、提供删除入口；团队功能须获成员授权
最后一个判断 B3 的价值不在「算得准」——市面上能算变量的工具有，只是中文的少。
它的真正价值在于：把你的解读方法论产品化了。客户用工具看到结果，然后用你的话术体系理解结果——这两者绑在一起，才是别人抄不走的东西。
所以内容层（24 项文案）比计算层更值得投入。计算可以外包，文案必须你自己写。
